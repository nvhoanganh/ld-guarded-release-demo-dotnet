# Guarded Release Demo — LaunchDarkly Terraform

Manages the LaunchDarkly feature flag and metric this demo depends on, as code.

## Prerequisites

- [Terraform](https://developer.hashicorp.com/terraform/install) (`brew install hashicorp/tap/terraform`)
- A LaunchDarkly **personal API access token** (Admin role), either exported as
  `LD_API_KEY` or placed in a `.env` file at the repo root as `LD_API_KEY=api-...`
  - Generate at: app.launchdarkly.com → Account Settings → Authorization → Access tokens

> The API token is *not* the SDK key. The SDK key lives in `appsettings.json`
> (see the root README) and is only used by the app at runtime.

---

## First-time setup

```bash
cd devops/terraform
terraform init
bash apply.sh
```

`apply.sh` reads `LD_API_KEY` from the environment, falling back to `../../.env`,
then runs `terraform init -upgrade`, `plan` and `apply`.

Non-default project/environment:

```bash
terraform apply \
  -var "ld_api_key=$LD_API_KEY" \
  -var "ld_project_key=my-project" \
  -var "ld_environment_key=production"
```

## What is managed here

| File | Contents |
|------|----------|
| `main.tf` | Provider (`launchdarkly/launchdarkly ~> 3.0`) and variables |
| `flags.tf` | `new-checkout-flow` boolean flag + its environment targeting (off, serving `false`) |
| `metrics.tf` | `http-latency-checkout` numeric metric (lower is better, unit `ms`) |
| `apply.sh` | Convenience script: init + plan + apply |
| `sync_flags.sh` | Pulls flags that exist in LD but not in Terraform and generates resources |
| `terraform.tfvars` | Auto-generated by `sync_flags.sh`, gitignored — do not commit |

### `new-checkout-flow`

Read in `Program.cs`:

```csharp
var useNewFlow = ld.BoolVariation("new-checkout-flow", context, false);
```

Variation 0 = `true` (new v2 engine: 300–800 ms, ~20% HTTP 500).
Variation 1 = `false` (old v1 engine: 50–100 ms, stable). Off and fallthrough
both serve variation 1, so a fresh apply leaves the demo in its baseline state.

### `http-latency-checkout`

Built on the event key `http.latency;route=/api/checkout`, which the
LaunchDarkly Observability plugin derives from the ASP.NET Core server span —
there is no `ldClient.Track()` call in app code.

**Ordering caveat:** that event key only exists in LD once the app has sent
trace data (~30 s of running). If `terraform apply` rejects the metric with an
unknown event key, run `dotnet run` and hit `/api/checkout` a few times first,
then re-apply.

## What is NOT managed by Terraform

| Resource | Why | Where to manage |
|----------|-----|-----------------|
| The **Guarded rollout** on `new-checkout-flow` | The LD Terraform provider does not expose guarded rollout / release guardian config | LD UI → flag → Targeting → Default rule → Serve *Guarded rollout* |
| Observability auto-metrics | Generated from ingested OTel data | LD UI → Telemetry → Observability metrics |

Guarded rollout settings used for the demo (configure in the UI):

- Target variation: **true**
- Target by: **request** (matches the metric's analysis unit)
- Metrics to monitor: `http-latency-checkout`, ✓ Auto rollback
- Stages: `5% → 10% → 25% → 50% → 100%`, 5 minutes each

## Common workflows

### Push local changes up to LaunchDarkly

```bash
bash apply.sh
# or: terraform plan / terraform apply
```

### Pull flags created in the LD UI down into Terraform

```bash
bash sync_flags.sh   # writes imports.tf + generated_flags.tf, then runs plan
terraform apply      # imports into state
```

Then move the resources from `generated_flags.tf` into `flags.tf`, delete
`imports.tf` and `generated_flags.tf`, and confirm `terraform plan` reports
`No changes`.

### Import a single existing resource

```bash
terraform import launchdarkly_feature_flag.new_checkout_flow default/new-checkout-flow
terraform import launchdarkly_feature_flag_environment.new_checkout_flow_env default/new-checkout-flow/production
terraform import launchdarkly_metric.http_latency_checkout default/http-latency-checkout
```

If the flag or metric already exists in LD from a manual setup, import it before
the first apply — otherwise apply fails with a conflict.

### Check for drift

```bash
terraform plan
```

`No changes. Your infrastructure matches the configuration.` = fully in sync.
